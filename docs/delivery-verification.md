# Verificação de entrega em andamento

Este documento registra evidências de preparação; não aprova a entrega nem os gates pendentes.

## Publicação e verificações parciais de 06/11/2026

- A pedido do usuário, o projeto existente `frontend-challenge` da equipe `elaranjo-1483` recebeu um deployment de produção a partir do commit `d1810afe72bffa7bc8d4cb61f12b2aaccaeda716` de [elaranjo/front-end-chalenge](https://github.com/elaranjo/front-end-chalenge). O deployment `dpl_Dp4RWdYbEvoCDrSSHuxSu4o8nTEk` ficou `READY` e sua metadata identificou esse repositório e commit. A URL [frontend-challenge-one-tau.vercel.app](https://frontend-challenge-one-tau.vercel.app/) respondeu HTTP 200 sem autenticação e exibiu a página inicial em português.
- No Chromium com viewport mobile e contextos isolados na URL pública, uma compra simulada foi confirmada com um único POST de pedido. No cenário de recusa, o recibo de compra recusada apareceu e o item permaneceu no carrinho. No cenário de resposta expirada, apareceu o aviso de recuperação, a tentativa ficou salva e o reload recuperou o recibo com apenas um POST observado. Carteira e carrinho foram preparados pela API simulada nesses três testes; eles não substituem uma nova execução pública completa de ponta a ponta.
- Como visitante em Chromium desktop, acesso direto e refresh de `/`, `/login`, `/signup`, `/cart` e `/nfts/emerald-ape-042` retornaram HTTP 200 e mantiveram a rota. Acessos diretos a `/wallets`, `/profile`, `/favorites`, `/checkout` e `/orders/missing` retornaram HTTP 200 e redirecionaram para login; o refresh foi feito no login, portanto não comprova refresh das rotas protegidas com sessão. Um reset público com `{ "scenario": "default", "clockMode": "real" }` retornou HTTP 200 e o estado consultado indicou `default`. Uma primeira tentativa sem `clockMode` retornou 422, como entrada incompleta; não foi tratada como reset bem-sucedido.
- Em uma verificação posterior na URL pública, após autenticação fictícia, acesso direto e refresh de `/profile`, `/wallets`, `/favorites` e `/checkout` retornaram 200, mantiveram a rota e apresentaram os respectivos títulos. `/orders/missing` manteve a rota e exibiu o estado de erro recuperável. Em contexto mobile separado, uma compra simulada gerou um recibo; o refresh retornou 200, preservou a URL do pedido e exibiu novamente a confirmação. Nesse último teste, carteira e carrinho foram preparados pela API simulada.
- Os dois testes de `preview-realtime.spec.ts` foram executados em uma cópia temporária com a origem substituída pela URL pública e passaram individualmente. Um cliente Socket.IO carregado pelo teste conectou por WebSocket, recebeu `nft.updated` e `order.updated`, reconectou após desconexão simulada, revalidou sessão/assinaturas e recebeu outro evento; a assinatura de pedido de outra conta foi recusada. O segundo teste observou evento de outbox em outra aba. Os dados são fictícios, isolados no contexto do navegador e controlados pela API simulada; isso verifica o transporte público com cliente de teste, não prova por si só toda a interface de pedido pendente durante uma desconexão.
- Uma cópia temporária dos cenários de pedido pendente de `checkout-recovery-ui.spec.ts`, adaptada para a URL pública, passou em 390 × 844 e 1440 × 900. Após criação pela interface, o socket interceptado da aplicação foi observado fechado; o relógio simulado avançou e a API confirmou o pedido enquanto não havia socket aberto. A abertura posterior e o recibo do mesmo pedido foram observados com apenas um POST. Como o módulo-fonte de runtime não está disponível no build publicado, a adaptação conferiu o estado do socket, sem consultar `realtime.isReady`; carteira e carrinho foram preparados pela API simulada.
- Em uma cópia isolada existente, com árvore versionada limpa e HEAD alterado para o commit publicado `d1810af`, `.env` conferido como idêntico a `.env.example`, Node 24.22.1 e npm 11.19.1, `npm ci`, typecheck, lint, build e os 106 testes focados passaram. O lint apresentou sete avisos de Fast Refresh e nenhum erro. O lockfile teve SHA-256 `742c3f413dbf6e3596d7ac4876a7465c01db544222c83a352defbfb50d4c52ec`; `dist/index.html`, `b02c79fbcc496f433f2730dcfa0ce65bf039cd55ef03f6e76ace5d105587090e`. No preview dessa cópia, o detalhe abriu e foi recarregado com HTTP 200 e service worker controlador. A cópia já existia e teve dependências reinstaladas; não é uma clonagem nova pela URL remota nem uma execução integral E2E do commit publicado.
- Em seguida, uma clonagem nova com `git clone --depth 1` da URL GitHub de entrega obteve o mesmo commit `d1810af` e árvore versionada limpa. Após copiar `.env.example` para `.env`, com Node 24.22.1 e npm 11.19.1 passaram `npm ci`, typecheck, lint, build e 106 testes focados. O lint apresentou sete avisos, e o build avisou sobre um chunk acima de 500 kB. Os hashes de lockfile e `dist/index.html` coincidiram com os da cópia isolada anterior. No preview dessa clonagem, detalhe direto e refresh retornaram 200, o service worker controlou a página e a API simulada respondeu 200. Não foi executada a suíte E2E integral nessa clonagem.
- Na prévia do mesmo commit foram observados service worker controlando a página, API de catálogo, acesso direto e refresh do detalhe e recebimento de `nft.updated` por um cliente Socket.IO. Também foram exercitados o percurso completo de compra pela interface, recusa, recuperação de timeout e pedido pendente com desconexão simulada. O reset retornou ao cenário `default`. A observação parcial da desconexão na prévia, por si só, não prova toda a sequência de reconexão exigida em G07.
- O projeto Vercel mantém a vinculação Git anterior ao repositório original. Este deployment foi criado com a origem e o SHA do repositório de entrega explicitamente informados; pushes posteriores no novo repositório não foram configurados para publicar automaticamente.
- Estas observações não aprovam G07: a auditoria completa da entrega e dos gates anteriores continua pendente. G04 e G05 também permanecem pendentes. As observações mais antigas abaixo descrevem o estado anterior à publicação deste commit.

## Antes de considerar a entrega pronta

As tarefas 11.1–11.3 e 11.5 permanecem abertas, inclusive as limitações de acessibilidade documentadas em [reports/accessibility/revisao-manual.md](../reports/accessibility/revisao-manual.md). Para G07, registrar o commit final e os links efetivamente entregues; verificar instalação a partir desse commit, correspondência do build público, acesso direto e refresh de rotas, assets e service worker, compra confirmada e recusada, timeout, reconexão e reset. Registrar os resultados observados, sem assumir que o deployment existente contém as alterações locais.

Na conferência anterior ao commit de implementação, somente `README.md` estava versionado. O commit incluiu código, lockfile, assets, testes, OpenSpec e relatórios; `.env.example` documenta a configuração pública dos mocks e `.env` permanece ignorado. As pastas de configuração `.agent/` e `.agents/` foram preservadas localmente fora do commit. Os relatórios e traces preservados representavam aproximadamente 268 MiB naquela conferência. O commit foi preparado como versão em andamento; G04, G05 e a publicação ainda precisam ser concluídos.

Em uma nova conferência local em 06/11/2026, os comandos `check:figma-assets`, `check:figma-geometry` e `check:figma-typography` terminaram sem erros. O primeiro verificou hashes e inventários, incluindo 15 referências, 197 SVGs públicos, quatro imagens NFT, seus derivados e fontes; a busca de caminhos literais em `src` não cobre referências dinâmicas. Os demais verificaram a geometria de cinco assets específicos e inventariaram a tipografia extraída. Essas checagens não comprovam fidelidade visual nem a presença dos arquivos em um commit ou repositório de entrega.
